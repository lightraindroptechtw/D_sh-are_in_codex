# DSH 介面為何無法直接使用：本機唯讀調查

日期：2026-10-28。本文依本機現存原始碼與語料判斷，沒有下載新的第三方插件、啟動第三方程式或呼叫模型。統計不是實際相容率。

## 結論與適用範圍

DSH 插件的前端通常是交給 DSH 載入的模組，還需要 DSH 提供畫面位置、服務、元件及後端連線。只把前端 JavaScript 檔放進瀏覽器，或只替工具建立 MCP（工具連接協定）連線，並不會補齊這些需求。

本機 CC 版已實作「逐插件照原始碼補寫」流程，使用 Claude Code 自己的能力重做功能；它仍然沒有把所有 DSH 原前端直接承載起來。Codex 這次新增的也是補寫流程。獨立網頁有實作空間，但通用的 DSH 前端承載器尚未完成；需要掛在聊天輸入框、訊息或工具結果內的功能還要另外處理宿主能力。

此處 CC_ROOT 取自 `<local-workspace>` 的 `d-sh-are-in-cc.installLocation`，本次值是：

```text
<local-cc-source>
```

CODEX_ROOT 為本文件所在套件的根目錄：

```text
<local-workspace>
```

本文的行號為調查當下所讀版本；後續編輯可能使行號移動。

## 前端實際向 DSH 借了哪些能力

`__ModuleLoader__.load`（前端模組載入器）負責把插件模組交給宿主；`require`（程式庫取得函式）可能向宿主要 React、網頁掛載器或 DSH 元件。載入後，`slots`（畫面插槽）決定元件放在哪裡，`services`（宿主服務）提供資料與操作，`remote`（前後端呼叫與事件橋接）把介面接回插件後端。

這些並非只要提供同名空函式就能相容。具體例子：

| 本地語料檔案，相對於 `work/dsh-corpus-100/sources/` | 行號 | 直接使用的能力 |
| --- | --- | --- |
| `dsh-api-client_0.2.0/dist/client.js` | 1、33 | 前端載入器、`react-dom/client`（React 網頁掛載器）。 |
| 同上 | 58-95、6680、6945、7000-7003 | 插槽規格、目前畫面樹、插槽內元件及變更訂閱；只做 `inject/register`（注入／登記）不足以滿足。 |
| `dsh-client-ui-second-brain_1.0.2/lib/client.js` | 7、1104、1148-1158 | React、插槽服務，同時註冊設定頁與目前對話標頭的動作按鈕。 |
| `dsh-ai4scholar_0.3.8/lib/client.js` | 267、983-1005 | 後端憑證服務、連線介面、`remote.credentials`（遠端憑證服務）與憑證更新事件；缺少它們會影響實際儲存與更新金鑰。 |
| `bgjobs_0.2.6/lib/client.js` | 921、2030 | `@deepseek-ai/dsh-client-ui-primitives`（DSH 基礎介面元件庫）及其開關元件。 |

例如第二大腦插件的設定畫面可以另做成網頁，對話標頭按鈕則需要選擇替代操作入口，還要把「目前是哪個對話」與所需內容明確接過來。把這兩部分都叫成「支援介面」會掩蓋實際差異。

`client-usage.mjs` 以特定 JavaScript 載入器文字樣式辨識前端，按模組識別去重；有深度、檔案大小及目錄略過規則。`ui-categories.mjs` 找到帶 `dsh` 欄位的套件，按套件名稱去重，使用 CC 自己的靜態檢查與純畫面分類；同名套件只保留先找到的版本。它們量的是不同集合，也不是全市場最新版。

167 個模組取得 React；47 個取得 DSH 基礎介面元件庫。只支援最常見前 8 個服務名稱時，有 72/176 個模組的「被腳本抓到的服務名稱」全部落在該集合；這不是 72 個可直接運作的插件。

腳本另以插槽與服務名稱的允許清單估出：

- 46/176 個符合「只用頁面類位置與基本服務」的靜態候選規則。它們仍可能需要未被文字樣式捕捉的依賴、事件、後端或掛載語義。
- 93/176 個使用對話、輸入框、工具呼叫位置或相關對話服務。替它們開獨立網頁，不能自動保留在原對話位置的行為。
- 這兩個集合不必互補；沒有符合其中一項，不代表必定符合另一項。

388 與 176 的差異來自分類對象與辨識規則不同，不能相減得出「漏轉多少畫面」，也不能把 46/176 稱為已驗證的獨立網頁相容率。

## 現有解法與尚未實作的方案

| 方式 | 本次可確認的狀態 | 可處理的情形 | 仍無法保證的情形 |
| --- | --- | --- | --- |
| 保留插件原有工具與技能 | 既有轉換器已實作；仍須逐插件驗證 | 有畫面也有獨立工具的插件，可先使用工具部分。 | 原前端、聊天位置、所有 DSH 服務語義。 |
| 使用插件本來就提供的本機網頁 | 已有路由服務與路由控制工具 | 頁面本身獨立、確實有對應網頁資產與後端路由。 | 只有 DSH 前端模組、仍要宿主提供所有服務的插件。 |
| 按來源逐插件補寫 | CC 已有流程；Codex 本次新增核心與市場串接 | 把設定頁或面板重做成獨立網頁；把對話按鈕重做成可明確呼叫的技能或工具。 | 不經開發就原樣呈現所有 DSH 插件；宿主沒有開放的內嵌位置。 |
| 通用獨立頁面適配器 | 待實作的方案／假說 | 可先挑不依賴對話內容的頁面類插件，逐項建立與驗證支援範圍。 | 缺少任何實際服務時，不能用空實作宣稱完整相容。 |
| 原樣嵌入宿主聊天輸入框、訊息、工具卡片 | 本次沒有實作 | 只能在宿主確實提供相應擴充點時另行設計。 | 開瀏覽器分頁並不會產生那些擴充點，也無法替換宿主模型與內部代理迴圈。 |

若未來要實作獨立頁面適配器，需明確逐項完成：前端模組載入、共用的 React 執行環境、插槽掛載與更新、資料注入與清理、元件庫及樣式、設定表單、前後端方法呼叫與事件、錯誤／取消、憑證與工作區範圍。這是建議方向，不是現有功能清單。

## 本次落地範圍與直接驗證

Codex 新增 `lib/rewrite.mjs`，提供來源檢查、準備可編輯任務、完成檢查及套用四個入口。補寫只可在指定的技能、執行期、資產與掛鉤資源目錄及結果檔改動；來源、準備基準與成果都以雜湊綁定。新增 MCP 以指定名稱合併，不能取代既有同名服務。掛鉤資源目錄本身不會自動掛載到 Codex 原生事件。

這個流程本身不呼叫模型、不執行新程式，模型與思考強度只是記錄使用者選擇。授權資訊會保留並告知，未知或自訂授權不由固定規則直接禁止。

本次直接驗證了 `tests/rewrite.test.mjs` 的 8 項核心測試，以及 `tests/market-rewrite-flow.test.mjs` 的 2 項市場流程測試：共 10/10 通過。市場流程使用真實來源快照、轉換器、補寫檢查與市場簽章；原生安裝命令與作業系統執行限制的邊界使用測試替身。另以 `verify` 真正啟動我們自己寫的合成 MCP 回音服務並收到回傳。

這是補寫流程、完整性與合成工具的證據；不是第三方介面相容率、真正 Codex 登記安裝或作業系統隔離的證據。後續主流程若另做正式驗證，應另附其結果。

本次建議保留逐插件補寫為可使用入口；未來將「可獨立顯示的頁面」與「必須嵌在聊天中的元件」分開建立具體驗證案例，再決定通用適配器的實作範圍。
